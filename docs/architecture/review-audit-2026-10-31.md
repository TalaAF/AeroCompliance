### Remaining correctness and security decisions

1. **Trusted proxy configuration for separate-container deployments: resolved locally.** The Compose backend network now reserves `172.30.250.254` for frontend nginx (configurable with its subnet); the API trusts that exact address. Both nginx configurations replace inbound `X-Forwarded-For` with the immediate peer address. Integration tests verify separate IP-based login limits, the audit IP through the trusted proxy, rejection of spoofed headers from an untrusted peer, and loopback behavior. The actual network change has not been deployed; an existing Compose network will need a planned recreation while retaining its named data volumes. Check for subnet overlap before deployment.
2. **Token/session model:** refresh-token family reuse response and migration from browser `sessionStorage` to an HttpOnly cookie need explicit semantics for CSRF, logout, concurrent refresh, and compromise handling. The tooltip XSS vector is fixed, but tokens remain readable by any future script injection. This is pre-existing risk and a separate security design decision.
3. **Multi-instance correctness:** outbox claiming, worker request deduplication, and report locking remain process-local or at-least-once. A single API/worker topology is unaffected by cross-instance races; resolve these before deploying multiple replicas.
4. **Retry ambiguity:** a transient connection failure after a committed refresh can leave the client without its new token; a similar review response can return a conflict after a successful first commit. Preventing this requires an idempotent response contract. The atomic database state and no-duplicate-decision properties are covered by the tests.
